# Épica E3: Actaira Cloud funcionando en local, de principio a fin

**Para Claude Code.** Se ejecuta con `/epica E3`. Antes, lee:

- `CLAUDE.md`;
- `docs/harness/LECCIONES.md`;
- `docs/estado/E2.md` y `docs/LLM.md`;
- en `docs/PLAN.md`: la sección 0 (quién es quién y "El contrato de capacidades"), la sección 3 (ADR 16), la sección 9 entera y el bloque C9.

## Objetivo

La primera plataforma self-serve de pago, **con el builder primero** (`docs/PLAN.md`, sección 0). Una empresa se da de alta con GitHub, conecta repos y la Action sube el lockfile. Con eso tiene:

- para el builder: subinquilinos, un contrato por cliente y un pasaporte por agente v1 que puede enseñar a sus clientes, con su marca, un enlace verificable y un badge;
- flota, historial de capacidades y la máquina del tiempo sobre el historial de lockfiles;
- alertas, también cuando una versión nueva de un MCP que usa añade una capacidad irreversible;
- la IA incluida;
- una prueba de 7 días con topes, y paga con tarjeta: el plan Builder primero y Team como segundo plan.

Todo sin tocar la infraestructura del cliente y con un coste fijo casi cero.


**Esta épica termina con la plataforma entera funcionando en local con Docker**, probada de extremo a extremo. El despliegue en Azure es la E4.

## Prerrequisitos

- E2 cerrada.
- Repo `actaira/actaira-cloud` (privado), clonado en `~/actaira-ws/actaira-cloud`, y Claude Code abierto **dentro** de él (`cd ~/actaira-ws/actaira-cloud && claude`). Si la sesión está en otro repo, para y pide a Marcos que la abra ahí.
- Cuentas en modo test, sin coste: Stripe (modo test) y una clave de Mistral para el eval del LLM. Claude Code le dice a Marcos cuándo hace falta cada una y cómo sacarla.
- Nada de Azure todavía.

## Arquitectura (resumen; los ADR la justifican)

- **Backend:** Go, arquitectura hexagonal.
  - `domain/` sin dependencias;
  - `ports/`: `Store`, `Billing`, `LLM`, `Mailer`, `Clock`, `Budget`;
  - `adapters/`: Postgres con `pgx`, Stripe, Azure OpenAI, Mistral, correo.
- **Reutiliza el núcleo** importando `github.com/actaira/actaira/pkg/...`.
- **Frontend:** React, Vite, TypeScript y Tailwind, compilado y embebido en el binario con `go:embed`. Una sola imagen de contenedor.
- **Base de datos:** Postgres en Neon, en la región de la UE, con el endpoint con pool.
  - Migraciones con `goose`, embebidas, ejecutadas por el **endpoint directo** de Neon con el rol propietario; la app usa el endpoint con pool.
  - **RLS forzado por inquilino:** `ENABLE` y `FORCE`, políticas con `USING` y `WITH CHECK` sobre `current_setting('app.tenant_id', true)`, y el contexto se fija con `SELECT set_config('app.tenant_id', $1, true)` dentro de cada transacción (`SET LOCAL` no admite parámetros). Sin contexto, no se ve nada.
  - **Rol de aplicación creado por SQL,** nunca desde la consola ni la API de Neon, porque esos roles heredan `BYPASSRLS`: `CREATE ROLE actaira_app LOGIN NOBYPASSRLS NOINHERIT;` con `GRANT` mínimos. Las tablas pertenecen a otro rol. La CI comprueba, conectada como la app contra Neon, que `SELECT rolbypassrls FROM pg_roles WHERE rolname=current_user` devuelve falso.
  - **Cuota de Neon:** el plan gratuito limita el cómputo al mes y suspende tras unos minutos sin uso. Por eso ni la sonda de estado ni `/healthz` tocan Postgres, y los latidos y sondeos se agregan en memoria y se escriben por lotes. El ADR 16 recalcula el cómputo mensual con esas frecuencias antes de E5. Si se supera, se pasa al plan de pago de Neon o a Azure PG con créditos, detrás del puerto `Store`.
- **Autenticación del usuario:** GitHub App (inicio de sesión de usuario más instalación en la organización).
- **Subida del lockfile desde la Action, sin secretos en el repo del cliente:**
  - la Action pide un token OIDC de GitHub (`id-token: write`) con audiencia `https://app.actaira.com`;
  - la nube verifica la firma con las claves públicas de GitHub y exige `iss=https://token.actions.githubusercontent.com`, `aud` exacto y `exp`;
  - `repository_id` y `repository_owner_id` tienen que coincidir con los IDs de la instalación de la GitHub App. **Nunca se usan nombres**, que cambian;
  - guarda `ref` y `event_name`. Las subidas desde un PR van al historial del PR, nunca al de la rama por defecto;
  - rechaza un `jti` repetido;
  - en PRs desde forks no hay token OIDC: la Action avisa y sigue;
  - alternativa para GitLab y otros: un token de API por inquilino.

## Pasos

### Paso 3.0 (en el repo `actaira`, en su propia sesión): servidor MCP y skill

`actaira mcp serve` expone por stdio `discover`, `diff` y `explain` para Claude Code y Cursor, más una skill de ejemplo. Sin nube, así que puede salir antes que el resto de la épica.

### Paso 3.1: esqueleto, desarrollo local y ADRs

- Repo `actaira-cloud` con **el mismo harness que E0**, instalado con `install.sh` (reglas, hooks, subagentes, skills, `FALLOS.md`, `make check` y `make gate` con sus tests), incluido el hook `pre-push` que rechaza `main`, porque en un repo privado del plan gratuito no hay protección de ramas. Tras instalarlo, reinicio de sesión, `/hooks` y `make test-harness`, como en el paso 0.1, sin ningún push real a `main` ni orden destructiva de prueba (L-014).
- **Etiqueta base** `e3-base` en el primer commit de `main`, para que `cierre-epica` tenga con qué comparar.
- `docker compose` con Postgres local, Mailpit, migraciones, datos de ejemplo y `make dev`.
- **ADRs:** hexagonal; RLS; OIDC para la subida; SPA embebida; Neon frente a Azure PG (con el coste medido); correo.

### Paso 3.2: inquilinos, usuarios y GitHub App

- **Modelo de datos:**
  - `tenant` (la organización de GitHub), `user`, `membership` con roles;
  - `subtenant` (cliente del builder), `repo`, `agent`, `lockfile_version`, `finding`, `acceptance`, `alert`, `usage_event`;
  - `contract` (el contrato de un agente para un subinquilino, en formato ACM) y `passport`.
- **Registro de la GitHub App: lo hace Marcos en la interfaz de GitHub.** Claude Code le da:
  - el formulario exacto: nombre, URL de callback, URL del webhook, permisos mínimos (`metadata: read`, `contents: read` si se lee el lockfile, y nada de escritura) y eventos;
  - dónde guardar la clave privada y el secreto del webhook (Key Vault; en local, `.env` fuera del repo).
- **Tests de fuga entre inquilinos:** consultas cruzadas con dos inquilinos y dos subinquilinos que deben devolver 0 filas. Van en la CI.

### Paso 3.3: ingesta y diff en la nube

- **`POST /v1/lockfiles`** con OIDC:
  - valida el esquema del lockfile;
  - lo guarda versionado;
  - calcula el diff con la versión anterior usando el núcleo.
- **Idempotencia** por hash del lockfile y límites de tamaño y de frecuencia.
- **Paso opcional en la Action (`upload: true`)** que sube el lockfile. Si la nube no responde, la Action no falla el PR: avisa y sigue.

### Paso 3.4: el builder primero: contrato por cliente y pasaporte v1

- **Agrupación por cliente (subinquilino)** para builders.
- **Contrato por cliente:** el del repo (bloque `intent` de `actaira.lock`) es la base, y por cada subinquilino el builder escribe en la consola el que acuerda con ese cliente, en el mismo formato ACM. Lo acepta una persona, y la consola guarda quién y cuándo (`docs/PLAN.md`, sección 0, doctrina 1). Sin contrato, el agente sale "sin contrato", no como error.
- **Pasaporte por agente v1,** por subinquilino:
  - capacidades potenciales, el contrato y si el agente lo cumple, y la vista de cobertura (`docs/cobertura.md`), sin porcentajes ni veredicto de conjunto;
  - con la marca del builder;
  - enlace verificable: se abre sin cuenta y dice de qué commit y de qué hash de `actaira.lock` sale, para que quien tenga el repo lo compare. La firma criptográfica llega en la E7;
  - un badge para el README o la web del builder, que enlaza al pasaporte;
  - HTML imprimible, que el navegador guarda como PDF. El **informe por cliente** reúne los pasaportes de sus agentes. El PDF generado en el servidor queda en backlog, porque un Chromium sin interfaz en Container Apps añade coste y fragilidad.
- **Tests obligatorios,** en rojo antes de construir: el pasaporte de un subinquilino no enseña nada de otro; un agente sin contrato sale "sin contrato"; el pasaporte y el informe fallan el test si enseñan un porcentaje de cobertura o un veredicto de conjunto.

### Paso 3.5: consola

- **Pantallas:**
  - flota (agentes por repo y por cliente);
  - ficha de agente con capacidades potenciales, contrato, historia y diff;
  - **máquina del tiempo:** qué podía hacer cada agente en un commit o una fecha, sobre el historial de lockfiles guardados;
  - flujos tóxicos y alcanzabilidad;
  - blast radius potencial;
  - aceptaciones con su caducidad;
  - la vista de cobertura en la ficha de cada agente (`docs/cobertura.md`), con la antigüedad de cada fuente, sin porcentajes ni veredicto de conjunto.
- **Accesibilidad básica y los dos idiomas.**

### Paso 3.6: alertas

- **Correo transaccional:**
  - en local, un capturador de correo (Mailpit) en `docker compose`, para probar los correos sin enviarlos;
  - en producción (E4), Azure Communication Services Email desde **`mail.actaira.com`**, un subdominio propio verificado con registros DNS en Cloudflare y sin buzón; el dominio gestionado de Azure solo para pruebas, porque sus límites de envío son muy bajos;
  - con dominio propio empieza con un límite bajo de envíos por minuto y por hora. El `Mailer` encola respetando límites configurables. Cuando haga falta más, Marcos pide el aumento a soporte con el texto que le prepara Claude Code;
  - el remitente es `no-reply@mail.actaira.com` con `Reply-To` a la dirección de contacto que configure Marcos (variable de entorno, nunca en el repo), que es también el contacto de soporte; no hay correo corporativo.
- **Webhook de Slack o Teams** que pega el cliente.
- **Resumen diario:** prioridad determinista y como mucho tres acciones.
- **Aviso por MCP:** cuando el rastreador de `actaira-kb` publica una instantánea en la que una versión nueva de un servidor MCP añade una capacidad irreversible, se avisa a cada inquilino cuyo lockfile usa ese servidor. Cada aviso sale de los datos de su propio inquilino, con el RLS de siempre; la consulta que busca a quién avisar no cruza datos entre inquilinos. Test obligatorio, en rojo antes de construir: dos inquilinos con el mismo MCP reciben cada uno su aviso, y ninguno ve nada del otro.

### Paso 3.7: IA con el modelo más eficiente

Cumple `docs/LLM.md` entero.

- Puerto `LLM` con adaptadores para Azure OpenAI (despliegue en la zona de datos de la UE), Mistral y cualquier API compatible con OpenAI (sirve para Ollama en local).
- **Pieza 1, clasificador de tools desconocidas:** la salida es `inferred` y cumple la **monotonía**, así que solo puede subir la gravedad.
- **Pieza 2, explicación del diff:** una frase citando identificadores del grafo. Si una cita no valida, se usa la plantilla fija.
- **`make llm-select`** elige el modelo (ver `docs/LLM.md`). En esta épica compara Mistral y un modelo local con Ollama; los de Azure OpenAI entran en la E4, cuando haya suscripción. El elegido se guarda en configuración con el resultado del eval que lo justifica.
- **Medición de coste por llamada:** tokens de entrada y salida por el precio de la tabla de configuración, en `usage_event`.

### Paso 3.8: prueba de 7 días, cuotas y presupuesto global

- **Topes por cuenta**, tal como están en el `PLAN.md` (sección 9):
  - 7 días;
  - 3 agentes y 3 repos;
  - 200 subidas;
  - 7 días de historial;
  - tope en euros de IA;
  - pocos MB de almacenamiento.

  Los valores están en configuración, no en el código.
- **Presupuesto global mensual de las pruebas:** una tabla `budget` con lo gastado del mes. Cada operación con coste lo descuenta antes de ejecutarse. Si no hay presupuesto, las pruebas nuevas van a lista de espera y las activas quedan en solo lectura.
- **Antiabuso:**
  - una prueba por organización de GitHub;
  - antigüedad mínima de la cuenta;
  - límites por IP y por token.
- **Al acabar la prueba:** solo lectura, pantalla con lo detectado y botón de contratar. Los datos se borran a los 30 días, avisando antes.
- **Informe diario de coste real por cuenta de prueba**, visible para Marcos en una página de administración.

### Paso 3.9: cobro

- **Planes** (`docs/PLAN.md`, sección 9): el **plan Builder**, el primero, y **Team**, el segundo. Los dos con el precio que pone Marcos en `config/pricing.yaml`; Claude Code no inventa precios, y sin precio en la configuración el plan no se activa.
- **Stripe:**
  - Checkout en modo suscripción para Builder y para Team;
  - Customer Portal para gestionar la suscripción;
  - webhooks con verificación de firma e idempotencia.
- **Checkout** con `tax_id_collection[enabled]=true`, `tax_id_collection[required]=if_supported`, `billing_address_collection=required` y `customer_creation=always`.
- **La decisión de impuesto es explícita en el puerto `Billing`:**
  - cliente en España: IVA del 21 %;
  - cliente de otro país de la UE con `eu_vat` verificado: inversión del sujeto pasivo;
  - si no se puede decidir, no se activa la suscripción.

  Stripe solo valida el formato del NIF-IVA al pagar; la comprobación contra VIES llega después, así que se escucha `customer.tax_id.updated`. Stripe Tax es opcional y lo decide Marcos.
- Cómo se emite la factura oficial lo decide Marcos con su asesoría antes de activar el modo live (E4).
- **Productos y precios** creados por script con la API de Stripe, primero en modo test. **El modo live lo activa Marcos**, que es quien tiene la cuenta verificada. Claude Code le da los comandos para crear los productos en live.

### Paso 3.10: modelo de amenazas y operación en local

- Modelo de amenazas de la nube en `docs/threat-model-cloud.md`: subida del lockfile, fugas entre inquilinos, webhooks falsificados y abuso de las pruebas. Cada amenaza con el test que la cubre.
- Endpoints `/healthz` (sin tocar la base de datos) y `/readyz`.
- Telemetría opt-in del open source con su endpoint, recuento anónimo, apagada por defecto.

## Pruebas de extremo a extremo que añade esta épica

`make e2e-rapido` (en cada `make gate`) ejecuta la ruta feliz de `e2e-local` con un inquilino. `make e2e-completo` (en `cierre-epica`) ejecuta todo lo de abajo.


- `make e2e-local`: levanta `docker compose`, crea dos inquilinos, sube lockfiles de `demo-agent` con un token OIDC de prueba (emisor simulado en tests), crea dos subinquilinos con su contrato y abre sus pasaportes sin cuenta, recorre la API de la consola, dispara alertas (Mailpit las recibe), también el aviso por MCP, agota una prueba y paga el plan Builder con Stripe en modo test.
- Tests de fuga entre inquilinos con dos inquilinos y dos subinquilinos, también sobre los pasaportes.
- Pruebas de la interfaz con Playwright sobre las pantallas principales.

## Riesgos conocidos que ya están resueltos en esta épica


| Riesgo de bloqueo | Cómo queda evitado |
|---|---|
| La nube no puede importar paquetes `internal/` del núcleo | El núcleo expone `pkg/` desde la E1 |
| En repos privados gratuitos no hay protección de ramas, entornos ni aprobaciones | Producción con `workflow_dispatch`, hook `pre-push` y credencial federada atada solo a `main` |
| El sujeto OIDC nuevo de GitHub no coincide con credenciales federadas de formato clásico | Sujeto inmutable con los IDs de owner y repo, y prueba de humo |
| Los presupuestos de Azure no se admiten en suscripciones de créditos | Módulo aparte que no bloquea el despliegue, más controles propios |
| La identidad del sistema no existe al crear la app | Identidad asignada por el usuario, creada antes y con los roles asignados |
| Rol de Neon con `BYPASSRLS` que deja el RLS sin efecto | Rol creado por SQL con `NOBYPASSRLS` y comprobación en la CI |
| La cuota gratuita de Neon se agota por sondas y latidos | Sondas que no tocan la base, escrituras por lotes y cálculo previo en el ADR |
| West Europe sin capacidad para entornos nuevos | Orden de regiones sin West Europe |
| Uso de nombres de repo mutables en el OIDC | IDs de repo y owner, historial de PR separado y rechazo de `jti` repetidos |
| Tirar de una imagen privada de GHCR exige un token que caduca | ACR Basic con identidad gestionada, pagado con créditos |
| El certificado gestionado no se emite ni se renueva con el proxy de Cloudflare | Registro sin proxy de forma permanente |
| Los créditos caducan antes de usarse | Se activan justo antes del primer recurso de Azure |
| Arranque en frío de Container Apps y de Neon | La Action no falla si la nube tarda; Stripe reintenta los webhooks; se responde rápido y se procesa después |
| El modelo elegido no está en la zona de datos de la UE o no hay cuota | Comprobación previa con az CLI; `llm-select` incluye un segundo proveedor (Mistral), así que siempre hay alternativa |
| Log Analytics dispara el coste | Tope diario de ingesta y retención mínima |
| Crear el registro de aplicación de Entra exige permisos | Marcos es propietario de su inquilino; si falla, Claude Code le da el comando exacto para asignarse el rol |
| Stripe live no se activa sin verificar la identidad | Todo se desarrolla en modo test; el live es un paso de Marcos al final |
| Facturación española (Verifactu) | Decidida por Marcos con su asesoría; el código solo depende del puerto `Billing` |
| La verificación del dominio de correo se atasca | El puerto `Mailer` admite un proveedor alternativo |
