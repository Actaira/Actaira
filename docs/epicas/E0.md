# Épica E0: el harness, antes de la primera línea de producto

**Para Claude Code.** Esta épica no usa `/epica`, porque es la que la instala. Ejecútala a mano siguiendo estos pasos.

## Objetivo

Que el repo `actaira/actaira` tenga, antes de empezar el producto, el sistema que obliga a construir limpio:

- reglas;
- hooks;
- subagentes revisores;
- skills del bucle;
- registro de fallos con guardias;
- `make check` y `make gate`;
- CI.

Todo **probado**: cada pieza del harness tiene un test que demuestra que funciona.

## Prerrequisitos

| Qué | Cómo se comprueba |
|---|---|
| WSL con Go, Docker, `jq`, `gh` y `git` | `go version && docker info && jq --version` |
| `gh` con permiso `workflow` | `gh auth status` muestra `workflow` en los scopes |
| Repo `actaira/actaira` público, clonado en `~/actaira-ws/actaira`, con `main` y un README | `git -C ~/actaira-ws/actaira log --oneline -1` |
| Claude Code abierto **dentro** de `~/actaira-ws/actaira` | `pwd` |
| El paquete descomprimido en `~/actaira-ws/paquete/` | `ls -a ~/actaira-ws/paquete/harness` muestra `.claude` |

Si falta algo, para y dale a Marcos los comandos exactos de `00_PREVIA.md`.

## Pasos

Cada paso va en su rama `e0/paso-<M>-<nombre>` y entra por PR, empezando por el 0.1 (`git switch -c e0/paso-1-harness` antes de instalar).

### Paso 0.1: instalar el harness y recargar la sesión

- `bash ~/actaira-ws/paquete/harness/scripts/harness/install.sh ~/actaira-ws/paquete ~/actaira-ws/actaira`. Copia con `cp -a` (incluye `.claude/`), deja `PLAN.md`, `LLM.md` y `epicas/` en `docs/`, crea `.gitattributes` y `.gitignore`, y el hook `pre-push` que rechaza `main`.
- Comprueba: `ls -a .claude scripts/harness docs/harness docs/epicas` y `jq . .claude/settings.json`.
- Commit, `git push -u origin e0/paso-1-harness`, PR y fusión (todavía sin CI, así que sin `gh pr checks`).
- **Para aquí** y pide a Marcos: "Cierra Claude Code y vuelve a abrirlo con `cd ~/actaira-ws/actaira && claude`, y dime `sigue con la E0`". Los hooks y permisos solo se cargan al arrancar.
- **Al volver**, antes de seguir:
  - `/hooks` lista PreToolUse (`guard-git.sh`), PostToolUse (`post-edit.sh`) y Stop (`stop-gate.sh`);
  - cada hook se prueba solo con sus tests, que llegan en el paso 0.3 (`make test-harness`). Nunca con un push real a `main` ni con ninguna otra orden destructiva de prueba (L-014).
  Si algo no cuadra, para y avisa: sin harness cargado no se construye nada.

### Paso 0.2: `make check` y `make gate` mínimos

- **`Makefile`** con:
  - `check`: formato, lint, tests, `test-harness`, `gitleaks` como binario fijado con checksum, `scripts/harness/check-weakeners.sh` y `scripts/harness/check-fallos.sh`;
  - `gate`: `check evals-paso e2e-rapido`;
  - `evals-paso`, `e2e-rapido` y `e2e-completo`: vacíos al principio, que pasan diciendo "sin evals todavía" o "sin e2e todavía" (con `@echo`, nunca con `|| true`);
  - `install-hooks`: reinstala el `pre-push`.
- **Módulo Go vacío** con un test trivial, para que la cadena funcione de punta a punta.

### Paso 0.3: probar el harness (cada pieza con su test)

Los tests van en `scripts/harness/tests/`, cada uno en un directorio temporal (`mktemp -d`) y sin tocar el repo, y se ejecutan con `make test-harness`, que forma parte de `check`.

- **`check-weakeners.sh`:** un Makefile con `|| true`, otro con una receta con `-`, otro con `.IGNORE`, otro con `$(MAKE) -k`, un workflow con `continue-on-error: true` y uno limpio. Todos fallan menos el limpio.
- **`check-fallos.sh`:**
  - entrada sin guardia: falla;
  - `test:` a un test Go que no existe: falla;
  - `test:` a un test Go con `t.Skip`: falla;
  - `test:` a un test Go que pasa: pasa;
  - id repetido: falla;
  - el ejemplo dentro del bloque de código del formato no cuenta.
- **`stop-gate.sh`:**
  - sin `check:` en el Makefile: sale con 0;
  - repo temporal con cambios y `make check` que falla: 2, 2, 2 con el mensaje de escalado, y el cuarto intento sale con 0;
  - con `.harness/pausa-marcos`: sale con 0 y muestra el motivo;
  - tras un verde, el mismo árbol no vuelve a ejecutar `make check` (caché) y el contador vuelve a cero;
  - árbol limpio y sin commits sin subir: 0.
- **`post-edit.sh`:** un `.go` mal formateado queda formateado; un `.go` con error de sintaxis devuelve JSON con `additionalContext` y sale con 0.
- **`guard-git.sh`:** con JSON de entrada simulado, sale con 2 para `git push --force`, `git push -f origin x`, `git push origin +x`, `git push origin main`, `git -C . push origin main`, `git push --no-verify`, y para cualquier push estando en `main`; sale con 0 para `git push -u origin e0/paso-2-x` en una rama y para comandos que no son push.
- **`install.sh`:** instalado en un repo temporal, deja `.claude/settings.json`, los scripts ejecutables y el `pre-push`; reinstalado, no pisa un `FALLOS.md` con entradas.
- **Permisos:** `.claude/settings.json` es JSON válido y contiene las denegaciones y el hook PreToolUse (se comprueba con `jq`).

### Paso 0.4: CI y protección

- **Workflow `ci.yml`:** un único job llamado `check` en `ubuntu-latest` que ejecuta `make check`, con acciones fijadas por SHA y `permissions: contents: read`. El job de macOS (no obligatorio) llega en la E1, con el ADR de compilación.
- **Protección de `main`** (JSON en `docs/estado/branch-protection.json`), aplicada con `gh api -X PUT repos/actaira/actaira/branches/main/protection --input docs/estado/branch-protection.json`:
  - `required_status_checks`: `strict: true` y el check `check`;
  - `enforce_admins: true`;
  - `required_pull_request_reviews` con 0 aprobaciones;
  - `allow_force_pushes: false` y `allow_deletions: false`.
- Comprueba con `gh api repos/actaira/actaira/branches/main/protection` que todo quedó puesto.

### Paso 0.5: primer fallo registrado de verdad

Registra con la skill `registrar-fallo` el primer fallo real que haya salido en esta épica. Si no ha salido ninguno, registra uno provocado: rompe a propósito `check-weakeners.sh` y comprueba que su test lo caza. Así queda probado que el ciclo de registro y guardia funciona antes de usarlo en serio.

### Paso 0.6: cierre y etiqueta

- `docs/estado/E0.md` con la salida real de cada punto del "Listo cuando".
- Tras fusionar: `git switch main && git pull --ff-only && git tag e0-cerrada && git push origin e0-cerrada`. Es la base de comparación del cierre de la E1.

## Riesgos conocidos que ya están resueltos

| Riesgo | Cómo queda resuelto |
|---|---|
| Un hook de parada que deja a Claude Code en bucle infinito | Contador por sesión: al tercer bloqueo manda el mensaje de escalado, y el siguiente intento de parar se permite |
| Harness copiado pero no cargado (sesión abierta fuera del repo, o sin reiniciar) | Reinicio obligatorio tras el 0.1, `/hooks` y los tests de cada hook (`make test-harness`) |
| Un push a `main` o forzado que salta las reglas de permisos | `guard-git.sh` antes de ejecutar, `pre-push` local y `enforce_admins` en GitHub |
| El hook de parada que castiga una pausa legítima para Marcos | Fichero `.harness/pausa-marcos` con el motivo |
| Hooks que fallan en silencio | Cada hook tiene su test en `make test-harness` |
| La CI que se debilita con el tiempo | `check-weakeners.sh` dentro de `check`, con su propio test |
| Fallos que se registran sin guardia real | `check-fallos.sh` dentro de `check` |
| Revisiones que se convierten en bucle | Tres rondas como máximo, escritas en las skills y en `CLAUDE.md` |
