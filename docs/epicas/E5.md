# Épica E5: runner y capacidades efectivas

**Para Claude Code.** Se ejecuta con `/epica E5`. Antes, lee:

- `CLAUDE.md`;
- `docs/harness/LECCIONES.md`;
- `docs/estado/E4.md`;
- en `docs/PLAN.md`: el bloque C3, las ADR 9 a 11 y la tabla de conectores.

## Objetivo

Confirmar, contra los sistemas reales del cliente y sin sacar sus secretos, lo que la credencial de cada agente permite de verdad. Además:

- avisar cuando un permiso cambia sin que nadie toque el código;
- entregar al builder el informe por cliente con capacidades efectivas.

## Prerrequisitos

- E4 cerrada: la plataforma en producción.
- **Orden de conectores fijo, sin depender de lo comercial:** primero **GitHub App** (ya instalada), luego **AWS IAM** (tiene simulador oficial). Si más adelante un cliente pide otro, entra por el backlog.
- **Repo principal:** `actaira` para el runner (abierto) y `actaira-cloud` para la parte de la nube; cada uno en su sesión. `make e2e-runner` vive en `actaira-cloud` y usa la imagen del runner publicada por etiqueta.
- **Modo por defecto de los conectores:** el runner consulta cada sistema **con la credencial del propio agente**, en la infraestructura del cliente y en solo lectura. Así Actaira no necesita registrar apps OAuth en Salesforce, Zendesk ni HubSpot.
- Una GitHub App de prueba con permisos acotados y una cuenta AWS de prueba, creadas por Marcos con las instrucciones exactas de Claude Code.

## Pasos

### Paso 5.1: runner (en el repo abierto, Apache-2.0)

- **Qué es:** `actaira runner`, un binario Go en la infraestructura del cliente.
- **Cómo se instala:**
  - imagen pública en GHCR (es código abierto);
  - chart de Helm;
  - unidad de systemd.
- **Alta del runner:**
  1. token de un solo uso generado en la consola;
  2. el runner genera su par de claves (ECDSA P-256) y manda la petición de certificado;
  3. la nube firma un certificado de cliente para ese inquilino;
  4. desde entonces, **mTLS**, y **el inquilino se deriva del certificado, nunca del payload**.
- **Dónde termina el mTLS:**
  - el runner habla con una Container App aparte, `runner.actaira.com`, con `clientCertificateMode: require` y sin proxy de Cloudflare de forma permanente. La consola mantiene `ignore`;
  - el ingress de Container Apps pasa el certificado en la cabecera `X-Forwarded-Client-Cert` pero no valida la cadena. **La app la valida ella misma** contra la CA de Actaira: cadena, caducidad, revocación e inquilino según la SAN. Solo acepta esa cabecera si viene del ingress;
  - un test envía un certificado autofirmado ajeno y espera un 401.
- **Salida controlada:**
  - lista de destinos permitidos por conector, publicada y configurable;
  - soporte de `HTTPS_PROXY` corporativo;
  - un test de red comprueba que no sale tráfico fuera de la lista.
- **Latido** hacia la nube. Si se pierde, el estado del inquilino pasa a `error` y se avisa.
- **Secretos:** se leen de variables de entorno, ficheros montados o el gestor de secretos del cliente. **Nunca** salen del runner ni van a logs; lo comprueban centinelas en los tests.
- **Rotación del certificado** automática, con aviso si falla.

### Paso 5.2: qué credencial usa cada agente

- El lockfile ya sabe qué variables de entorno referencia cada agente, por ejemplo `STRIPE_API_KEY`.
- El runner lleva un `runner.yaml` del cliente que dice de dónde sale cada variable y a qué sistema pertenece. Así se une lo potencial (el código) con lo efectivo (la credencial).
- Lo que no está en `runner.yaml` sale como `unseen`: una fuente `not_configured` con ese motivo, en la vista de cobertura.

### Paso 5.3: conectores de solo lectura (uno a uno: GitHub y luego AWS)

- **Cada conector lleva su README con:**
  - el permiso mínimo;
  - la documentación oficial enlazada;
  - una cuenta de prueba;
  - un test con cambios provocados.
- **Guarda la respuesta de la API** (redactada y con hash) como respaldo de cada capacidad `effective`.
- **Cada variable que `runner.yaml` asigna a un sistema pasa a ser una credencial, y cada credencial es una fuente de la vista de cobertura** (`docs/cobertura.md`). El conector es la forma de leerla, no otra fuente. Si `runner.yaml` dice que una variable no es una credencial, sale de la cuenta con ese motivo. Los servidores MCP siguen `not_configured` en esta épica.
  - Lleva estado, motivo y antigüedad.
  - Pasa a `stale` cuando su última lectura correcta supera la antigüedad máxima de su tipo, que se fija aquí a partir del sondeo de 15 minutos.
  - Con estas fuentes llegan los ejes **efectivas**, contadas sobre una lista cerrada y versionada de pares por conector, y **efectivas no usadas**, resaltadas.

| Sistema | Fuente real | Nivel | Nota que evita un bloqueo |
|---|---|---|---|
| GitHub App | Permisos de la instalación por API | `effective` | Ya instalado en la E3 |
| AWS | `SimulatePrincipalPolicy` con claves de contexto explícitas y `ResourcePolicy` cuando aplique; se guardan `MatchedStatements` y `MissingContextValues` | `effective`, o `conditional` si falta contexto | Límites de peticiones del API de IAM: caché y espera entre reintentos |
| Kubernetes | `SubjectAccessReview` sobre una lista cerrada de pares (verbo, recurso), más lectura de Roles y Bindings | `effective`, o `partial` con autorizadores webhook | El runner solo necesita `create` sobre `subjectaccessreviews` y leer RBAC; **nunca** `impersonate` |
| Salesforce | Describe del objeto como el usuario de integración del agente, más `ObjectPermissions` y `PermissionSetAssignment` | `effective` a nivel de objeto; el acceso a registros concretos queda declarado | **Primer paso:** comprobar en una org Developer gratuita que el describe por REST refleja al usuario (lo confirma la documentación de Apex) y cuál es el permiso mínimo para consultar `ObjectPermissions`. Con la credencial del agente no hace falta app propia. Si algún día Actaira se conecta por su cuenta: External Client App empaquetada, porque Salesforce ya no deja crear Connected Apps nuevas |
| HubSpot | Tokens OAuth: introspección; apps privadas (legacy): el endpoint de información del token | `effective` | Con la credencial del agente, sin app propia. Si Actaira se conecta por su cuenta: app pública de HubSpot, que registra Marcos |
| Zendesk | Rol del usuario, además de los scopes | `effective` para lo que define el rol | Con la credencial del agente, sin app propia. Si Actaira se conecta por su cuenta: cliente OAuth global, que **Zendesk tiene que aprobar**; lo pide Marcos |
| Stripe | Tipo de clave (`sk_` o `rk_`), declaración del cliente y 403 observados | `declared` | La documentación no permite leer los permisos de una clave restringida |

### Paso 5.4: deriva sin cambio de código

- Sondeo cada 15 minutos o menos por fuente, y webhooks donde existan.
- **Alerta tipo "`support-prod` ha adquirido `customer.delete`"**, con:
  - la ruta en el grafo;
  - la fuente del cambio;
  - la hora;
  - el blast radius.

### Paso 5.5: mínimo privilegio (IA, pieza 3)

- **Sin IA:** se calcula la diferencia entre lo que la credencial concede y lo que usan las tools del agente. Es el eje **efectivas no usadas** de la vista de cobertura. Solo da número si se ha visto todo lo que podría usar la credencial (las condiciones están en `docs/cobertura.md`); si no, esos permisos salen como uso desconocido.
- **Con IA:** se redacta el cambio de permisos (política IAM, permission set, clave restringida).
- El cambio se valida (simulador de IAM, `SubjectAccessReview`) y se enseña como diff de capacidades. **Nunca se aplica solo.**

### Paso 5.6: builder y subinquilinos

- **Consentimiento del administrador de cada cliente final** antes de consultar su Salesforce, Zendesk o HubSpot: un **registro firmado** de quién autorizó y cuándo (no es un flujo OAuth, porque se usa la credencial del agente).
- Informe por cliente con capacidades **efectivas** y la página de estado con la marca del builder.
- **Plan Builder con suscripción en Stripe:** base más importe por agente activo, con el precio que Marcos pone en la configuración (`config/pricing.yaml` y el producto de Stripe); Claude Code no inventa precios.

## Listo cuando

- Por cada conector activado, en un entorno real con cambios provocados:
  - 100 % de los cambios detectados en 15 minutos o menos;
  - 0 capacidades `effective` sin respuesta de API guardada.
- El test de red del runner, en verde.
- 0 secretos en eventos o logs.
- Rotación de certificado probada.
- Un subinquilino de prueba ve su informe efectivo con datos reales de la GitHub App y de la cuenta AWS de prueba.
- La vista de cobertura enseña, por agente, las fuentes de identidad con su antigüedad y las efectivas no usadas resaltadas, con un test por contador.
- Cierre con la skill `cierre-epica`.

## Pruebas de extremo a extremo que añade esta épica (entran en `make gate`)

- `make e2e-runner`: runner en `docker compose` contra la nube local y contra cuentas de prueba (AWS con LocalStack no vale para IAM: se usa una cuenta de prueba real de AWS con un rol de solo lectura; Kubernetes con `kind`; GitHub App). Cambio provocado de permisos y alerta recibida.
- Test de red del runner y de fugas de secretos.

## Riesgos conocidos que ya están resueltos en esta épica


| Riesgo de bloqueo | Cómo queda evitado |
|---|---|
| Los scopes OAuth no son capacidades | Fuente real por sistema; el scope es solo un dato |
| Registrar apps de Salesforce, HubSpot y Zendesk (con aprobación de Zendesk para el cliente global) | Por defecto, credencial del propio agente y sin apps propias |
| El ingress de Container Apps no valida la cadena del certificado de cliente | App aparte para el runner y validación de la cadena en la propia app |
| El runner no puede salir por el proxy del cliente | `HTTPS_PROXY` y lista de destinos documentada |
| El equipo de seguridad del cliente no aprueba el runner | Código abierto, SBOM, binario firmado, permisos mínimos por conector, solo lectura |
| No se sabe qué credencial usa cada agente | `runner.yaml` explícito; lo no mapeado sale `unseen` |
| La API de Salesforce no se comporta como sugiere la documentación | Se prueba primero en una org Developer; si no se cumple, el conector se marca `partial` y no se vende como efectivo |
| Límites de peticiones de las APIs | Caché, sondeo configurable y espera entre reintentos |
